## Technical Changes In This Increment

- Moved active-resume profile references into the owner-locked version transactions. Local/cloud imports now pass parsed profile fields into the upload transaction; activation and active deletion synchronize the chosen or cleared reference before commit. Removed the five post-service router writes that could overwrite a newer selection. Missing parsed fields preserve existing evidence and ordinary preferences remain untouched. Storage I/O remains outside the transaction; failed-upload compensation, uncertain commits, deletion/SQL failures, post-commit match refresh and audit recording are still separate recovery concerns.
- Bound Windows startup readiness to a fresh child-specific runtime identity. The launcher restores the parent identity after process creation (including failure), uses separate per-launch logs, and rejects responses from a different or already-exited process. The runtime validates launcher identities while retaining random identities for direct starts. Both Windows and ngrok require boolean readiness and exact, case-sensitive identity matches; ngrok also rejects malformed local identities. These are startup-correlation checks, not authentication or continuous monitoring.
- Patched the dependency findings for Browserslist, qs, xmldom and MySQL2. The refreshed audit reports no known advisories. Compatible transitive-version overrides are in `pnpm-workspace.yaml`; the lockfile is updated locally.
- Removed silent sample-data fallback when an explicitly configured database cannot initialize. Production without a database now fails at the database access boundary as well as configuration validation. Database-free development remains available.
- Extracted one shared runtime-schema validator used by the operator audit and production startup. Production validates tables, column types/nullability, declared indexes, and foreign keys before catalog writes, HTTP listening or worker startup. It performs no repair or migrations. Metadata queries and connection establishment have bounded timeouts and the startup connection is destroyed on completion/failure.
- Changed container health from process liveness to `/readyz`, including database availability and a four-second HTTP deadline. This still does not measure provider readiness.
- Excluded browser automation artifacts and backups from Docker build context.
- Added a separate MySQL acceptance job to CI. The database-test command rejects missing opt-in, a non-acceptance target, or production mode rather than reporting success from skipped tests.
- Repaired the shared AI adapter's ignored `maxTokens` / `max_tokens` options. Invalid or conflicting limits are rejected before provider traffic; the existing default is unchanged. Missing-key errors now identify the Forge credential actually consumed. HTTP error bodies and status text are discarded to avoid forwarding provider-echoed private input. This is not a direct OpenAI integration or measured AI-cost reduction.
- Added runtime completion validation at the shared AI boundary. Truncated, refused, malformed or empty completions cannot be returned as successful analyses. Requested function names/choices and JSON-object argument shape are checked, without executing any function. A real adapter-to-matching test proves a truncated but parseable analysis is rejected in favor of the labelled deterministic fallback.
- Enforced server-authored JSON Schemas for structured AI output and function arguments using Ajv. Validation rejects incorrect types, required-field omissions, prohibited extra fields and constraint violations without coercion or mutation. Compiled validators use a bounded 64-entry content-keyed cache; schemas are limited to 64 KiB and cannot load remote references or run asynchronous validation. All 19 current feature schemas are compiled by regression tests. Schema validity does not establish factual correctness, authorization or live-provider acceptance.
- Repaired PDF resume extraction for the installed `pdf-parse` v2 API. The former v1 function call failed on valid PDFs. The engine is now loaded only for PDF uploads, and its cleanup is awaited after success or failure. Real synthetic two-page extraction and the PDF-to-AI-to-profile path are tested; the AI HTTP response is mocked and no real candidate data or live provider is used. This is text extraction, not OCR for scanned image-only documents.
- Moved the first malware check ahead of document parsing and AI for both local resume imports and cloud imports. Failed scans prevent subsequent parsing, storage and profile changes. Independent storage-time scanning remains, so successful imported files are currently scanned twice. HTTP scanner responses now use the shared incremental 64 KiB reader and cancel unused/error bodies; a rejected response releases the scan permit. These are locally tested controls, not live scanner acceptance or a claim that scanning proves document safety.
- Applied the existing 500,000-character resume-text limit at the shared parser, covering file imports as well as pasted text. Uploads and direct extractors reject files over 10 MiB; PDFs over 60 pages are rejected before text extraction. DOCX ZIP preflight caps entries and declared expansion, then counts actual decompressed bytes while draining each entry to reject dishonest size metadata before Mammoth extraction. Empty extracted text is rejected before AI; artificial PDF page labels are disabled. Completely blank work and education records no longer become punctuation-only profile evidence. A blank-PDF router test verifies no AI call, stored version or existing-profile change, using in-memory profile persistence and mocked scanner/storage boundaries. This does not implement OCR or fully constrain PDF parser memory for every malformed structural input.
- Bound resume activation/deletion to immutable row IDs throughout Profile, tRPC and storage. Version-only requests are rejected. A delayed deletion rechecks the original ID and object key under the owner lock rather than deleting whatever later reused the version number. Three real-MySQL regressions cover delayed deletion and stale activate/delete requests; private object operations are mocked. The later profile transaction increment above resolves the separate post-service profile writes, not cross-system object/SQL atomicity.
- Closed the remaining metadata-only resume write path in `profile.update`. Supplied resume URLs/keys are rejected before any profile fields are saved; regular profile edits preserve the versioned resume reference. The error directs callers to versioned uploads. This does not retroactively validate legacy stored keys or resolve cross-system transaction concerns.
- Added a separate erasure boundary check for legacy stored references. Cleanup requires the task and run to belong to the same user, a valid source-record ID, and a normalized key inside the applicable `resumes/<userId>/` or `attempts/<userId>/` namespace. Unsafe or mismatched keys fail the task rather than calling storage or permitting database finalization. Owned keys retain the existing leading-slash normalization, null keys remain no-ops, and provider failures remain retryable. This enforces the application's key convention, not provider-side permissions; unusual legacy keys require operator review and are not automatically rewritten.
