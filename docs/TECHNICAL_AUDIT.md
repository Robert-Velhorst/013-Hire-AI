# Technical Audit

Audit date: 2026-08-08

## Runtime and boundaries

- Frontend: React, Vite, Tailwind, shadcn components.
- API: Express and tRPC. Protected procedures require a session; admin procedures require the `admin` role.
- Persistence: Drizzle/MySQL with an intentionally explicit in-memory development fallback.
- Jobs: policy-driven public discovery sources only. Account-gated and unsupported sources remain unavailable until an approved adapter exists.
- External effects: Hire.AI prepares, reviews, and records employer handoffs. It does not claim an employer submission, email delivery, provider connection, or interview without recorded evidence.

## Audit findings closed in this change

| Finding | Resolution |
| --- | --- |
| Settings exported only browser-loaded profile and application data while claiming all data. | `privacy.exportData` now builds an authenticated server-side export and records an audit event. Private document bytes, storage keys, OAuth grants, and credentials are excluded. |
| No operational HTTP probes. | `/healthz` and `/readyz` now return bounded JSON status; readiness identifies development-memory persistence rather than presenting it as a database. |
| No baseline HTTP response hardening. | The server disables `X-Powered-By` and applies anti-framing, MIME, referrer, permissions, cross-origin, production CSP, and HSTS headers. |
| Session security inferred HTTPS from any request-supplied `X-Forwarded-Proto` header while Express had no trusted-proxy contract; HTTPS cookies also used unnecessarily broad `SameSite=None`. | Express now trusts forwarded metadata only from loopback, matching the local ngrok process. Cookie security uses Express's trusted `req.secure` result and every session cookie uses `SameSite=Lax`, preserving OAuth top-level navigation while reducing spoofing and cross-site credential exposure. |
| Cookie-authenticated writes relied on browser SameSite behavior without a server-side request-origin check. | Every unsafe request carrying the session cookie now requires an exact effective-origin match before general body parsing and tRPC execution. Missing, opaque, malformed, and cross-site origins fail with `403`; signed Stripe and bearer-authenticated HAI routes remain ahead of this browser-session boundary. |
| Public API traffic had no inbound request-rate bound, allowing one client to monopolize a standalone or tunneled process. | Non-Stripe `/api` requests now receive a trusted-client fixed-window budget with deterministic `429`, reset, and retry guidance. The timer-free state store is capped at 10,000 clients with opportunistic expiry and oldest-client eviction; health checks and signed Stripe retries remain unaffected. Multi-instance deployments still require upstream distributed enforcement. |
| Every authenticated API request upserted the user solely to replace `lastSignedIn`, turning all reads and batched UI queries into database writes. | Session authentication still reloads the user on every request for immediate role, account-status, locale, and terms changes, but no longer writes activity. OAuth callback and first-user synchronization remain the only runtime paths that record the actual sign-in timestamp. |
| tRPC context creation swallowed every authentication exception, so database failures and identity-provider outages appeared as ordinary anonymous sessions and public procedures could continue under uncertain authentication state. | Only deliberate 4xx authentication failures now produce an anonymous context. Database and unexpected failures propagate, provider `401/403` remains an authentication rejection, and provider/network outages use a fixed `503` classification without exposing upstream details. |
| Signed session payloads carried an application ID but verification accepted any non-empty value, allowing another application sharing the signing secret to produce a Hire.AI-authenticated cookie. | Session verification now requires the signed application ID to exactly match the configured Hire.AI application before any user lookup or provider synchronization. Foreign-application tokens receive the same non-disclosing invalid-session treatment as malformed cookies. |
| Logout only deleted the current browser cookie, so a copied stateless token remained usable until its long expiry. | Every session now carries the user's persisted session generation. Logout atomically advances it and clears the browser cookie; all pre-logout copies fail immediately, while a newly issued session uses the current generation. |
| OAuth sessions and the SDK default remained valid for one year, with no bounded deployment policy and separate hard-coded cookie/token durations. | `SESSION_TTL_MS` now controls both JWT expiry and cookie age, defaults to seven days, and is restricted to 15 minutes through 30 days. Runtime validation and the production doctor reject malformed or out-of-range overrides; local QA sessions retain their explicit six-hour limit. |
| Production accepted any non-empty `JWT_SECRET`, including short values and the checked-in example placeholder, allowing weak session signing configuration to pass startup diagnostics. | Runtime startup and the production doctor now require 32-4096 characters, reject surrounding whitespace, control characters, and known placeholders, and report only policy status without disclosing the configured secret. |
| Primary sign-in constructed a base64 callback value as OAuth `state` in browser JavaScript, accepted it without browser binding, and depended on a portal URL baked into the production bundle even though deployment configuration is injected at runtime. | `/api/oauth/login` now reads a trusted runtime portal URL, derives the direct or loopback-proxy-approved callback origin, and issues HMAC-signed ten-minute state bound to an HttpOnly nonce. The callback clears the nonce and rejects unsigned, tampered, cross-browser, expired, future, or unsafe-callback state before token exchange; production bundles always use the same-origin initiation route. |
| Authentication reloaded `accountStatus`, but shared protected/admin middleware checked only identity and role; suspended users retained profile, connector, privacy, workspace, billing, and privileged API access outside selected job mutations. | Every protected and admin procedure now requires an exact active state before route logic. Public status/logout remain reachable, a localized routed-shell gate prevents operational query mounting, unknown authenticated states fail closed, and self-suspension cannot lock out the acting administrator. |
| Logout passed `maxAge: -1` to Express `clearCookie`, producing a runtime deprecation warning because Express expires cleared cookies itself and will ignore that option. | Logout now passes only the original path/security/SameSite attributes required to clear the matching cookie; focused and browser logout regressions complete without the deprecated option. |
| No local self-diagnostic command. | `pnpm doctor` checks runtime files, migration inventory, production-required configuration, bounded scanner settings, native Windows Defender availability, and the HAI/runtime gates without printing secrets. |
| No container build definition. | `Dockerfile` and `.dockerignore` provide a production Node 22 build path. |
| Production HTML embedded the Manus development runtime and a second React runtime. | Manus and JSX-location plugins now run only for the Vite development server. The production shell fell from 367,750 bytes to 487 bytes, and the build fails if development markers return or the shell exceeds 25 KiB. |
| Dashboard opened seven overlapping API queries and its ledger GET wrote campaign state. | Dashboard data now comes from one bounded operating snapshot, recent applications are projected and capped at 10, non-admin requests skip the global admin-review read, and the protected GET does not persist campaign state. |
| The embedded Vite server lost its root/plugins after production config became command-aware. | CLI and embedded startup now share `createViteConfig`; tests cover build/serve plugin boundaries and a live check verified `/src/main.tsx` is served as JavaScript. |
| Hot operating queries lacked matching compound indexes, several single-record workflows scanned full tables, and offer reviews queried responses once per approval. | Migration `0036` adds 17 query-aligned indexes. Privacy deletion, admin evidence, and duplicate-source aggregation now use bounded indexed lookups; offer-attribution evidence is loaded in one ownership-scoped batch. A regression test keeps migration and schema declarations aligned. |
| Operating-ledger queues independently reloaded responses, interview schedules, and follow-ups for each application. | The ledger now performs three ownership-scoped batch reads and groups their results once. Scheduling, outcomes, notifications, reply actions, and follow-up suppression share the same evidence snapshot. |
| Upcoming interview preparation checked for existing material once per interview. | Upcoming interviews and user preparations are loaded once in parallel, then matched by job ID in memory. |
| Offer-attribution projection reloaded applications, approvals, and responses already present in the operating snapshot. | The projection accepts preloaded data, re-filters it by authenticated user, and reuses the ledger's evidence snapshot. Campaign and post-evidence reads also run in parallel. |
| Admin operating snapshots loaded the global review table and filtered it locally. | The snapshot now requests at most 100 open/in-progress items for the affected user through the indexed `(user_id, status)` path. The separate global admin queue remains available for administrative operations. |
| Employment-verification resolution loaded the global review table to locate one entity's active reviews. | Resolution now requests only open/in-progress review items matching the affected user, verification entity type, and verification ID. The administrative global queue remains unchanged. |
| Standalone application lifecycle and admin evidence paths loaded every approval owned by a user before filtering one application. | A shared ownership-scoped lookup now loads only approvals linked by application ID or the legacy application-entity relationship. Submission confirmation, response cleanup, withdrawal, offer acceptance, follow-up completion, and evidence rendering use it. |
| Admin evidence loaded every application and decision for the affected user to identify one reviewed record. | Reusable owned application-ID and user/job decision lookups now use primary/unique keys. Evidence loads the application with approvals in parallel, then its artifacts with the exact decision in parallel. |
| Standalone lifecycle and approval mutations repeatedly loaded complete user application or approval collections to authorize one record. | Submission confirmation, response recording, interview and follow-up ownership, withdrawal, offer acceptance, approval resolution, and offer decline now use exact `(user, id)` lookups. Collection reads remain only where the workflow actually processes a set. |
| Application create, decision, and portal-preparation routes loaded all user applications to find one existing pending job record. | Each route canonicalizes the job and queries the existing unique `(user_id, job_id)` record with pending status directly, preserving duplicate-source idempotency without a history scan. |
| Save/ignore decisions reloaded all applications and all pending approvals to close one prepared review item. | The close branch now reuses the exact pending user/job lookup and loads approvals only for that owned application before cancelling its submission gate. |
| Employer reply preparation loaded every response for an application to select one target. | Reply preparation now retrieves either the explicit owned response or the newest owned replyable response with one bounded query; cross-user targets are rejected. |
| Interview preparation verified ownership and then loaded every schedule to select one future interview. | The successful path now joins the owned application to future scheduled/rescheduled interviews, orders by start time, and returns one row. Error semantics remain explicit. |
| Autonomous follow-up safety loaded responses, schedules, and follow-up history separately for every candidate. | One run now batch-loads each ownership-scoped evidence type once, groups rows by application, and reuses them across safety and cooldown decisions. |
| Every job-alert refresh loaded all active alerts, jobs, and platforms, even when no alert was due, and collected every matching job. | The scheduler now selects only due alerts through an indexed frequency/cutoff predicate, returns before job loading when idle, and uses first-match short-circuiting. |
| A non-idle job-alert refresh still materialized the complete active canonical-job corpus and issued one update per matched alert. | Current jobs are projected and traversed in deterministic 250-row ID pages; matched alerts leave the working set immediately and receive one bulk timestamp update. |
| The legacy discovery namespace duplicated the canonical Job Search API, retained callbacks in one server process, polled MySQL every 30 seconds, exposed unused public aggregate queries, and applied a weaker filter contract. | The duplicate module and namespace were removed. The wired `jobs` API now exclusively owns catalog reads and listing-safety filters; durable Job Alerts own match refreshes and retain the interview-only external-notification policy. |
| Every public platform-list and discovery-status request scanned platform names and conditionally upserted the scraper catalog even though runtime startup had already reconciled it. | Catalog reconciliation is owned by fail-closed startup and scraper initialization. Public reads now query persisted platform/status state directly without write-path contention. |
| CI verified only Ubuntu despite Windows 11 being a required standalone deployment target. | A dedicated Windows runner now installs from the lockfile, type-checks, parses both launchers, runs network and HAI contract tests, and builds the production bundle. |
| The dependency graph contained a critical Vitest advisory, a high nested-Vite Windows path advisory, and an ignored Nano ID override. | Vitest/Vite are patched, Nano ID 3 is forced to 3.3.17 through active workspace settings, and the advisory gate covers moderate or higher severity. |
| Remaining moderate runtime/tooling advisories affected Mermaid, DOMPurify, PostCSS, and esbuild, while pnpm 10 and 11 interpreted override locations differently. | Local and CI resolution now use pnpm 11, workspace overrides pin every patched path, only esbuild install scripts are allowed, and CI rejects moderate-or-higher advisories. |
| A source timeout abandoned the manager result but did not cancel the underlying fetch; fixed-delay retries ignored provider pacing and retried permanent HTTP failures. | Every network adapter now receives an abort signal, source scans are serialized, concurrency/deadlines are bounded, and transient-only retries apply abortable exponential and `Retry-After` pacing. Production doctor requires an explicit scheduled-source allowlist. |
| The authenticated routed shell nested primary landmarks, exposed brand navigation as a pointer-only `div`, named an account trigger only by its initial, and overflowed a 390-pixel dashboard with a non-wrapping status sentence. | Shared and dashboard headers now expose keyboard-named controls, the sidebar owns the sole primary landmark, long status badges wrap locally, and desktop/mobile browser smokes pass with a clean console and exact mobile document width. |
| The production Dockerfile pinned pnpm 10 without workspace overrides, did not enforce the doctor, and its pruned runtime still imported Vite. Fresh MySQL migration also failed on a multi-statement chunk and a 65-character foreign-key name. | The image now uses pnpm 11 with workspace policy, runs non-root with a health check and fail-closed doctor, carries a lock-protected migrator, and excludes the development Vite module. Migration boundaries and identifier limits are regression-tested; all 39 migrations and the live image passed MySQL 8.4 acceptance. |
| The Applications page loaded and rendered every joined ledger row, while deep links depended on that unbounded result. | The primary API now uses a 1-100 row keyset page ordered by `(created_at, id)`, whole-ledger statistics use one aggregate query, deep links use an exact owned lookup, platform names use a join instead of a row-wise subquery, and the UI loads older records explicitly. Migration 0039 aligns the composite index with that cursor; production-volume query-plan evidence remains deployment acceptance. |
| Dashboard snapshots and autonomous cycles still hydrated complete joined application, approval, and decision histories after the Applications page itself was paged. | Both paths now share an oldest-first 250-record active window, exact history for the current 250 jobs, exact daily preparation and whole-ledger counters, 100-row pending approval/review queues with exact totals, scoped approved follow-up handoffs, and explicit truncation. Migration 0040 adds the status/activity index; synthetic 260/105-item regressions pass, while representative MySQL query plans remain deployment evidence. |
| Inbox response discovery hydrated complete application/job records and checked every matched provider message with a separate employer-response query. | Each scan now selects only owned application ID/status and company/title, then deduplicates its bounded provider references into one indexed `(user_id, source, source_reference)` lookup. Heavy candidate/application fields stay out of scanner memory, tenant isolation is preserved, and up to 50 database round trips are eliminated. |
| Single-provider connector operations loaded every connector account and filtered by provider in application memory. | Inbox access, follow-up delivery, cloud documents, GitHub, LinkedIn, and OAuth callbacks now use the unique `(user_id, provider)` lookup directly. Full-list reads remain only where a workflow needs cross-provider readiness or account inventory. |
| Profile evidence refresh issued one match-ledger upsert per active job, up to the 250-job reconciliation window. | Deterministic matches now use atomic ten-row upserts, reducing the healthy-path write budget from 250 statements to 25. A failed batch falls back to per-job upserts so one malformed or unavailable row does not erase partial-success evidence. |
| Job Search loaded the user's complete application-decision history for every filtered result page. | The route now requires the current bounded job IDs and queries decisions through the owner/job set. Complete history remains available to privacy export without entering the interactive search response. |
| Report-hire stored an ISO currency but exposed no currency control and rendered every salary and fee as dollars; calendar defaults were derived from UTC. | A shared bounded billing-currency contract now drives UI and API validation, every billing amount uses its stored currency and account locale, and form calendar defaults use the local day. |
| Applications loaded the user's complete approval history even though its application ledger is paged. | The interactive route now requires at most 250 current application IDs and performs one owner/application-scoped query capped at 2,000 newest records. Pending, resolved, follow-up, and legacy application approvals remain available for the loaded UI without hydrating unrelated history. |
| The autonomous preview route loaded complete application, decision, and approval histories for every Job Search, Saved Jobs, and AI Preferences view. | Preview planning now shares the bounded operating primitives: 250 oldest active applications, exact current-job and approval-linked records, current-job decisions, an exact database daily-preparation count, and bounded operating approvals. The response discloses application and approval truncation instead of silently implying complete history. |
| Connector disconnect deleted encrypted grants locally without attempting provider revocation, making later cleanup impossible. | Disconnect now disables access first, performs bounded scoped revocation for Google, Dropbox, and GitHub, handles Google's shared grant, gives explicit manual guidance for Microsoft/LinkedIn, and retains failed grants only for auditable retry. |
| Three employer-handoff modules maintained different ATS catalogs and classified arbitrary URL substrings, so lookalike domains, paths, queries, and malformed text could produce false platform labels while iCIMS, BambooHR, and Jobvite varied by caller. | One shared parser now classifies only credential-free HTTP(S) hostnames at exact ATS domain boundaries. The public API, autonomous planner, browser-disabled handoff, and legacy compatibility layer agree on eight recognized platforms, all of which remain review/manual guarded. |
| HAI configuration accepted the documented placeholder as a production bearer token, allowed tokens the HTTP Bearer parser could never consume, parsed suffixed user IDs with `parseInt`, and advertised arbitrary local paths even though the server exposes only one A2A endpoint. | Runtime startup and `pnpm doctor` now share strict effective policy: a 32-4096 character non-placeholder token without whitespace/control characters, a canonical positive safe-integer user ID, and an exact credential-free local/private `/api/hai/a2a` URL. Diagnostics remain secret-safe. |
| The ngrok launcher considered any public endpoint returning `ready: true` to be the local Hire.AI tunnel, so a stale or misrouted reserved hostname could pass verification against another healthy service instance. | Each server process now generates a 192-bit opaque readiness identity. The launcher validates the local identity and reports public readiness only when the tunneled response echoes that exact value; mismatch receives explicit operator guidance. |

## Material unresolved risks

1. Production needs MySQL/TiDB, OAuth, Stripe, Forge, S3, malware scanning, and any enabled connector credentials.
2. A real browser or official API provider adapter needs separate policy, account, quota, and acceptance-test approval before activation.
3. Employment/payment retention and success-fee terms need legal and privacy review before real-user launch.
4. Hosted deployment, monitoring, and external-provider acceptance remain separate from the locally verified Windows Docker/MySQL runtime.
